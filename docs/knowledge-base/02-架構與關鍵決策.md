真正會失傳、也最容易讓後來者重新踩一遍的是決策背後的理由。

## 關鍵決策

### 決策 1：後台擴充靠「註冊表」，不靠把區塊寫在 JSX 裡

**做法**：`registry.ts` 定義分組，`modules/` 每個檔案匯出一個 `AdminModule` 物件，
外殼只做「身分閘 → 依註冊表渲染」。

**為什麼**：站長後台預期會持續長大，且型態多元（指標／表格／表單／日誌）。
硬寫版面的話每加一個模組就要動外殼，遲早變成難以維護的巨型元件。

**怎麼加一個模組**：
1. 在 `client/src/admin/modules/` 新增一個檔案，export 一個 `AdminModule`
2. 在 `client/src/admin/modules/index.ts` 的陣列加一行

**外殼與版面完全不動。** 這一點有測試守著。

### 決策 2：變化點收斂成「欄位」，不是「元件」

`AdminModule` 的每個欄位都是一個變化點：`group`（分類）、`order`（排序）、
`span`（半寬／整列）、`isAvailable`（依環境決定是否出現）、`render`（內容型態不限）。

**代價是刻意的**：外殼因此**不認識任何具體模組**。想新增一種版面，
不需要改外殼——那是 `render` 自由發揮的事。

### 決策 3：站長＝第三個「真正的角色」，不是多加一頁

**關鍵發現**：`adminProcedure` 早就在程式碼裡，但它是**死碼**——
它依賴的 OAuth 登入已被移除，實務上沒有人能成為 `admin`。

**做法**：復用既有的 `admin` 角色當站長（不另開 `owner` 製造平行概念），
新增**專屬**的 `ADMIN_PASSPHRASE`，未設定時 fail-closed。

**為什麼 fail-closed 是對的**：如果未設定也能進後台，等於後台門戶洞開。
「顯示尚未啟用＋給明確的設定指引」比「預設開放」安全得多。

### 決策 4：角色判定用「層級表」，不逐一列舉

`ROLE_RANK = { teacher: 1, admin: 2 }` ＋ `hasRoleAtLeast()`。

**為什麼**：原本每個 procedure 都要列舉允許的角色，
之後每加一個角色就要改多處、**很容易漏掉某一處**。改成登記層級後只需改一處。

### 決策 5：資源監控「搬家」＋ 端點「收緊」要一起做

原本 `dbUsage.status` 是 `publicProcedure`——**任何訪客**都能讀全站營運統計。
有了真正的站長身分後，卡片搬到 `/admin`，端點改為 `adminProcedure`。

**為什麼兩件事要一起做**：如果只把 UI 搬走、端點仍公開，
那「有後台」只是門面，資料仍然是公開的。

### 決策 6：知識用 markdown 放在 repo 裡，不寫死在前端

見 [README](README.md) 的說明。核心考量是**同一份內容要能被三種讀者消費**，
寫成前端常數就會變成只有「改程式才能更新」的孤島。

### 決策 7：後台不顯示機密，只顯示「是否已設定」

環境變數清單只回傳 `configured: true/false`，**永遠不回傳值**。

**為什麼**：後台是網站上的一個頁面。任何「顯示密鑰」的功能都是外洩管道，
而排查「某功能為什麼沒生效」其實只需要知道**是哪個變數還沒補**。

### 決策 8：統計只保留聚合，不記個體

請求統計只記狀態碼分級、HTTP 方法、耗時分布——**不記路徑、IP、User-Agent**。

**為什麼**：後台不該變成監控學生的工具。「站長想知道有沒有在噴錯」
不需要知道「是哪個學生在打」。

### 決策 9：先建 CI，再依賴它

2026-09-29 補了最小 CI（型別 → 測試 → 6 道閘門 → 建置），涵蓋的都是
「本來就寫好、但只有人工記得跑」的閘門。

**為什麼要強調順序**：一開始就紅的 CI 比沒有 CI 更糟。
所以在寫進 CI 之前，先在本機乾淨快照**逐一實跑**每一道，確認當下都是綠的。

### 決策 10：站長後台改用「純用戶名」驗證（2026-10-02，站長知情決定）

**做法**：移除 `ADMIN_PASSPHRASE`，改為比對站長用戶名（`ADMIN_USERNAME`，預設 `admin`）。
入口從「在 `/admin` 輸入通關語」改成**首頁左下角一個極低調的固定圖標**，
點擊後彈出輸入框，輸入自己的船名進設定、輸入站長用戶名進後台。

**⚠️ 這是安全性顯著下降的取捨**：沒有第二道因子，知道用戶名的人就是站長。
「隱藏的圖標」只是**降低被隨手試到的機率，不是安全邊界**。

**既然安全性靠不住，就補上可觀察性作為補償**：
- 每次 `admin.login`（成功與失敗）都寫進審計紀錄，站長在「維運操作審計」看得到
- 保留 `timingSafeEqual` 比對——即使只剩一道因子，也別洩漏長度以外的資訊
- **後端一定要真的驗證**：`CornerEntry` 輸入 `admin` 時必須呼叫 `admin.login` 換 cookie，
  不能只做前端跳轉（那等於前端自己宣告自己是站長）

**要收緊的話**：設 `ADMIN_USERNAME=<隨機長字串>`，
⚠️ **必須同時改前端 `CornerEntry.tsx` 的 `ADMIN_USERNAME`**，兩處不一致會讓首頁入口怎麼打都進不去。

## 已知且刻意不解決的問題

### 冷啟動延遲（Render 免費層）

閒置 15 分鐘後第一次請求會等 instance 喚醒。這是**目前最大、也唯一未改善的卡頓主因**，
與功能多寡無關。

- 免費層無法解決（要升級付費層）
- 線上已加的緩解：靜態題庫查詢 `public, max-age=60`、其餘 `no-store`
- 暖機後實測：TTFB 2 ms、FCP 44 ms——**站內本身很快，慢的只有喚醒**

### 跨科結合題數量不足

`qc:bank` 會報「應為 200，實際 120」。這是**內容缺口**，不是程式 bug，
且閘門 exit code 仍為 0（列為提醒不阻擋）。要補滿需要新增 80 題。
