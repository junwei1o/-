# 05 · 踩坑與陷阱

**這份是整個知識庫最常被需要的一份。**

寫法刻意是「症狀 → 根因 → 解法」而不是結論——
因為下次卡住時，人是**先看到症狀**才會想起這份文件。
如果你看到下面某一條的症狀，就已經對上了。

---

## A. 部署與環境

### A1. SPA fallback：未知路徑永遠回 200 + HTML

**症狀**：`/api/xxx` 或 `/assets/xxx.js` 明明不存在，`curl` 卻回 **200**。
以為部署壞了，其實沒有。

**根因**：`server/_core/index.ts` 的 `app.use("*")` 一律回 200 + `text/html`（SPA fallback）。

**解法**：**判斷「API／chunk 是否真的存在」必須看 content-type 或 body 是否 JSON，
不能只看狀態碼。** 這條會反覆踩到。

### A2. tRPC 方法用錯是 405，不是 404

**症狀**：端點明明存在，回 `METHOD_NOT_SUPPORTED`。

**根因**：tRPC **query 要用 GET、mutation 要用 POST**。

### A3. 加了依賴但沒更新 lockfile → 部署直接壞

**症狀**：Render 部署失敗，訊息指向 lockfile 不一致。

**根因**：`render.yaml` 用 `pnpm install --frozen-lockfile`。

**解法**：`package.json` 與 `pnpm-lock.yaml` 必須同步。
**要無頭瀏覽器請用 `agent-browser`，不要把 Playwright 加進專案。**

### A4. 部署版本判斷：單看 bundle 雜湊會誤判

**症狀**：改了純 server 程式碼，線上 bundle 雜湊變了，誤以為「前後端脫鉤」。

**根因**：兩件事——
1. `VITE_` 變數會被內聯進 bundle，所以**本機 build ≠ 線上 build**（除非本機也帶同樣的 env）
2. **純 server 改動本來就不會動前端 bundle**

**解法**：
- 純 server 改動 → 看 `last-modified` / `etag` / `rndr-id` 三者變化
- 要比對前端 → 建「不帶 env」與「帶 env」兩版對照，**比對多個 lazy chunk 檔名**，
  不要只看主 bundle
- 實測記錄：不帶 env 只有 44/92 對得上；帶上正確 `VITE_APP_ID` 後 **92/92 逐字相同**

### A5. 限流有沒有生效，看標頭就好

**症狀**：想確認限流，準備打 300 個請求。

**根因**：不必。看這兩個標頭即可：
`ratelimit: limit=300, remaining=…, reset=60` ＋ `ratelimit-policy: 300;w=60`

**但注意**：這兩個標頭**只掛在 `/api/trpc`**。打 `GET /` 讀不到——
本站後台的「安全防線」模組就踩過這個坑，一度把「問錯地方」誤判成「沒有設定」。

### A6. 本機 esbuild 版本抓錯會讓 bundle 啟動即崩

**症狀**：`node dist/index.js` 立刻 `ERR_MODULE_NOT_FOUND: Cannot find package '@shared/const'`。
看起來像程式問題，其實不是。

**根因**：`node_modules/.pnpm/` 下有多個版本的 esbuild，抓到舊的會把
tsconfig 的 `paths` 別名留成 external。

**解法**：用對版本
`node_modules/.pnpm/@esbuild+darwin-arm64@0.25.10/node_modules/@esbuild/darwin-arm64/bin/esbuild`

## B. 本機驗證

### B1. 「登入成功但閘門永不通」

**症狀**：`admin.login` 回 `{ok: true}`，但再問 `admin.me` 永遠 `isAdmin: false`。
cookie 也確實設上了。

**根因**：`verifySession` 要求 payload 的 `appId` **非空**，
而本機沒設 `VITE_APP_ID`。

**解法**：本機啟動務必帶 `VITE_APP_ID=<任意非空字串>`。

### B2. 非標準埠會讓所有 mutation 被擋

**症狀**：`CSRF_ORIGIN_REJECTED`（403），登入表單怎麼點都沒反應。

**根因**：`server/_core/csrfOrigin.ts` 的 `buildAllowedOrigins(host)`
**只把 `https://${host}` 加進白名單**，加上寫死的 dev 埠 5173 / 3000。
本機用 3999 這種埠走 http 時，瀏覽器送的 `Origin` 不在清單裡。

**解法**：本機 E2E 用 `PORT=3000`。
（這是 dev-only 限制，不是安全缺陷——若日後要支援任意 dev 埠，
改 `buildAllowedOrigins` 依 `req.protocol` 推導即可。）

### B3. React 受控輸入，用 `input.value = x` 不會觸發 onChange

**症狀**：在 `agent-browser eval` 裡填表單送出，表單沒反應。

**解法**：用原生 setter

```javascript
const setter = Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, 'value').set;
setter.call(input, '目標值');
input.dispatchEvent(new Event('input', { bubbles: true }));
```

### B4. 全站有登入閘，沒注入 session 會以為頁面壞了

**症狀**：`agent-browser open /admin` 之後看到的是「輸入你的船長名字」，
以為後台沒渲染。

**解法**：先開任一頁注入 `xue-session-v1` 到 localStorage（見 [03](03-本機工作台.md)）。

### B5. macOS 沒有 `timeout`

寫 `timeout 30 node ...` 會直接 command not found。用別的方式做逾時。

## C. 程式寫作

### C1. `React is not defined`（runtime 爆）

**症狀**：TS 編譯過、測試過，上線後白屏。

**根因**：本專案 `tsconfig` 是 `"jsx": "preserve"`，走**經典 JSX 轉換**，
**每個 `.tsx` 都要顯式 `import React`**。

**解法**：**對照既有檔案的寫法，不要憑通用知識。**

### C2. JSX 純文本裡寫 `**粗體**` 會原樣顯示星號

**症狀**：畫面出現 `這裡**很重要**` 這種字面文字。

**根因**：markdown 語法**不作用於 JSX children**。

**解法**：用 `<strong>`／`<em>`。

### C3. `Map` 迭代在 tsc 下要 `Array.from(...)`

**症狀**：`tsc` 報 downlevelIteration 相關錯誤。

**根因**：本專案 target 不支援 downlevelIteration。

### C4. `<dt>` / `<dd>` 必須在 `<dl>` 內

寫在 `<div>` 裡 tsc 不一定報錯，但語意與結構都是錯的。
`<meter>` 比自製進度條更合適（可省行內樣式）。

### C5. 測試抓到的失敗，先問「是測試錯還是設計錯」

**症狀範例**：後台測試因為「分組與模組同名（系統與環境）」而失敗。

**判斷**：這是**真設計問題**——畫面上也會讓站長混淆。

**解法**：修命名本身（分組改「系統與部署」、模組改「環境資訊」），
**而不是改測試讓它變綠**。修完順手加一條全域不變式測試防再犯。

### C6. 同名 heading 會讓 `getByRole` 多重匹配失敗

所以分組與模組不該同名。已用不變式測試鎖住。

### C7. 分組 `order` 不得重複

`order` 重複時顯示順序變成未定義（依陣列順序），
而且讀原始碼時會被誤導。已用不變式測試鎖住。

## D. 安全與隱私

### D1. `VITE_` 前綴 = 公開

Vite 會把所有 `VITE_` 變數內聯進前端 bundle，線上 bundle 已被驗證含
`VITE_APP_ID` 的值。**機密絕不可用此前綴。**

### D2. 新增了真正的角色，順手把公開端點收掉

**症狀（潛在）**：`dbUsage.status` 是 `publicProcedure` → 任何訪客都能讀全站營運統計。

**解法**：新增站長身分時，**端點權限要跟著一起改**。
只搬 UI 不改端點，等於「有後台」只是門面，資料仍然公開。

### D3. 公開端點別忘了「不帶參數」的情況

`aiTutor.tokenUsage` 是 `publicProcedure`，且不帶 `name` 時回傳**全站**統計——
學生打這個端點就能讀全站資料。

**解法**：分清「查個人」與「查全站」的權限；並**加匿名拒絕的回歸測試鎖**。

### D4. 探測目標要與宣稱一致

本站後台的「安全防線」原本只 `GET /` 讀標頭，
但**限流標頭只掛在 `/api/trpc`** → 永遠顯示「API 限流未回報」。

**解法**：分開打多個目標，並在畫面上標明每個目標的 HTTP 狀態，
讓「讀不到」與「沒設定」可以區分。**假阳性比沒有這個功能更糟。**

### D4b. ⭐ PAT 沒有 `workflow` scope 就不能改 `.github/workflows/`（2026-10-02 實測）

**症狀**：`git push` 被拒——
`refusing to allow a Personal Access Token to create or update workflow .github/workflows/ci.yml without workflow scope`

**根因**：GitHub 對 workflow 檔有額外保護，PAT 必須有 `workflow` scope 才能寫入。

**處理方式**：不要卡在這裡。**把 CI 改動獨立成一個 commit 之外的選擇**——
先把其他檔案提交推上去，CI 那行留給有權限的人手動加。
（用 `git reset --soft HEAD~1` ＋ `git restore --staged .github/workflows/ci.yml` 重寫提交。）

⭐ 這是「憑證權限不足」的一般教訓：**遇到權限牆時，先確認要做的改動是否必要**。
閘門可以先以 `pnpm qc:orphan` 的形式存在，本機與知識庫都記錄了，不會失效。

### D5. 憑證：PAT 寫進 remote URL

曾有 3 個 clone 的 git remote URL 內嵌明文 PAT，已清除。
複檢指令見 [03](03-本機工作台.md)。
⚠️ **兩種 URL 形式都要搜**（`x-access-token:ghp_…@` 與 `ghp_…@`），只搜一種會漏。
**已暴露的 token 必須在 GitHub 網站撤銷，API 無法自助撤銷。**

### D6. ⭐ `/api/backup` 無需認證即可下載全站原始碼（2026-10-02 掃描發現）

**症狀**：任何人 `curl /api/backup` 就拿到 **8.4 MB 的完整原始碼 ZIP**（含 `BACKUP_README.md`、
所有 `docs/`、`AGENTS.md`、知識庫）。沒有登入、沒有 token。

**這不是 bug，是刻意公開的功能**——站長要能一鍵下載、在本機離線架站。
`EXCLUDE_PATTERNS` 已排除 `.env`、`.git`、`*.log`，所以**機密不會跟著走**。

**但「刻意公開」不等於「應該無意識地公開」**：任何訪客（含學生）都能下載。
隱瞞這件事等於讓站長在不知情的狀況下做決定。

**現況處理**：已在站長後台「資料安全與備份」模組**明白寫出暴露範圍**，
並提供下載入口。要收緊的話：在部署環境設 `BACKUP_TOKEN`，讓 `/api/backup` 驗證它。
**不要擅自關掉**——關掉會直接破壞站長的離線架站流程。

### D7. ⭐ `Vary` 標頭必須「追加」，用 `setHeader` 會被覆蓋（2026-10-02 審查實測）

**症狀**：同一個 API，兩種客戶端拿到不同的 `Vary`：
```
curl（不帶 trpc-accept） → Vary: Accept-Encoding
瀏覽器（帶 trpc-accept） → Vary: trpc-accept, accept   ← Accept-Encoding 不見了
```

**根因**：壓縮中介層用 `res.setHeader("Vary", "Accept-Encoding")`，
而 **後設的 `setHeader` 會整個覆蓋先前的值，不是追加**。
tRPC 在自己的中介層裡也設了 `Vary: trpc-accept, accept`，於是把它蓋掉。

**後果不是理論問題**：中間快取（Render CDN、校園／家用代理）看到一個
`Vary` 沒有 `Accept-Encoding` 的回應，就**可能把 brotli 壓縮過的內容發給
不支援 br 的客戶端**，對方拿到的是亂碼。

**解法**：`Vary` 的語意是「所有會影響回應的請求標頭」＝**聯集**。
寫一個 `ensureVaryAcceptEncoding(res)`：讀現有值、沒有才加、然後合併寫回。
⚠️ 而且要在 **`decide()` 裡再呼叫一次**——因為 `decide()` 是在路由處理器
**之後**才跑的，只在中介層開頭設一次不夠。

### D8. 診斷端點不該阻塞全站

`tts.health` 曾經會同步等待安裝，導致**任何請求都被卡住**——
診斷功能本身變成 DoS 入口。診斷要能犧牲一點精度換取不阻塞。

## D. 時間與排序

### D8. `Date.now()` 只有毫秒解析度，不能單獨當排序依據

**症狀**：審計紀錄「由新到舊」排序失效，連續兩筆操作順序是反的。

**根因**：兩次操作落在同一毫秒時 `at` 相同，Array 的穩定排序會保留**插入順序**。

**解法**：加單調遞增的序號（`seq`）當 tiebreaker，排序依 `seq` 而非 `at`。

### D9. mutation 成功後要 invalidate 對應的 query，別只靠輪詢

**症狀**：站長按了「執行健康檢查」，轉頭看審計紀錄是空的——以為功能壞了。
實際上資料有寫入，只是該 query 靠 30 秒 `refetchInterval` 才更新。

**根因**：新增的端點沒加進 `onSuccess` 的 invalidate 清單。

**解法**：維運操作成功後 invalidate 會受影響的**所有** query。
⚠️ 順帶提醒：`useUtils` 的 mock 要記得補新增的端點——
**tsc 不會報錯，但執行時會炸**，只有真的點下去才會發現。

### E0. ⭐ 寫「孤兒 CSS 閘門」時必須懂動態拼接（2026-10-02 實測）

`qc-css-structure` 只檢查「選擇器有沒有被改壞」，**不檢查「CSS 裡的 class
是否真的有人用」**——所以刪掉一個模組後，它專屬的樣式會一直躺著。

但自己寫這道閘門時，**第一版一定會誤報**，因為有三種寫法會讓掃描器抓不到：

| 寫法 | 範例 | 抓不到的原因 |
| --- | --- | --- |
| 動態前綴 | `` `admin-md-h admin-md-h${n}` `` | `.admin-md-h1`～`h6` 在原始碼裡**不存在**這串字 |
| 條件類（字串有前導空白） | `` `${cond ? " is-open" : ""}` `` | 正則要求字串以字母開頭，**開頭那個空格**就讓整批漏掉 |
| 條件類（動態前綴以連字號結尾） | `` `is-${tone}` `` | 前綴正則要求 `-` 後面至少一個字符，**`is-` 匹配不到** |

**收斂的判準**（太寬太窄都會讓閘門失效）：
- 前綴要含連字號、長度 ≥ 3 → 排除 `${i}` 貢獻的 `"i"`（否則**所有** `is-*` 都被誤判為已使用，等於沒有閘門）
- 但要**允許以連字號結尾**（`is-`）→ 否則 `is-kb`／`is-ref` 全被誤報，而誤報會讓人直接關掉閘門

⭐ **閘門最危險的失敗模式不是漏報，是誤報**——人會因此把它關掉，那比沒有閘門更糟。

### E1b. ⭐ macOS 的 `zip` 不寫 UTF-8 旗標，Windows 解開會整片亂碼（2026-10-02 實測）

**症狀**：在 Mac 用 `zip -r` 打包中文檔名，丟到 Windows 用內建解壓後**全部變亂碼**。

**根因**：macOS 的 `zip` 預設把檔名存成 **Big5**，而且**不設 zip 的 UTF-8 旗標（bit 11）**。
解壓工具沒有旗標可依，就只能猜編碼——猜錯就是亂碼。

**驗證方法**（不要只看 `unzip -l` 的終端顯示）：
```python
import zipfile
z = zipfile.ZipFile('x.zip')
bad = [i.filename for i in z.infolist() if not (i.flag_bits & 0x800)]
print(len(bad))   # 0 才对
```

**解法**：用 Python 的 `zipfile` 打包，它會正確寫入 UTF-8 旗標。
跨平台交付的壓縮檔一律走這條路。

### E2b. ⭐ 審計腳本把 title/instruction schema 的題全判成「缺 prompt」（2026-10-15 實測）

**症狀**：重跑 `scripts/audit-question-bank-v2.mts`，回報 **104 個 error「缺少 prompt」**，
分散在前綴 `mx-*`(66)／`m-*`(30)／`sort-*`(5)／`img-*`(3)。
照字面看會以為有 104 題壞了。

**根因**：題庫有**兩種 schema**，審計腳本只認一種：

| 檔 | 題幹欄位 |
|---|---|
| `runtime_bank_elementary`／`generated_bank`（一般題） | `prompt` |
| `matching_bank`／`image_bank`／`sort_bank`／`generated_bank` 的跨科題 | `title` ＋ `instruction` |

實測 `sort-liangci` 的內容完全正常：
```json
{ "id": "sort-liangci", "title": "量詞搭配", "instruction": "把詞語放進正確的量詞籃", ... }
```
兩者都非空，只是**不叫 `prompt`**。所以這 104 筆是**誤報**，
佔了全部 119 個 error 的 87%——不先排掉它，根本看不到真正的問題。

**解法（已於 2026-10-15 修，見 E2d）**：
1. 審計腳本的題幹檢查改走 `stemOf(q)`（`prompt ?? title ?? instruction`），
   兩種 schema 都視為有題幹。
2. 或在題庫端統一補一個 `prompt` 別名欄位。

**⭐ 教訓**：這與 E0 的「閘門最危險的失敗模式是誤報」同型。
**審計報告的問題計數不能直接當待辦清單**——先抽樣驗證再排程，
否則會排到一批「修好等於把正常資料改壞」的工作。

### E2d. ⭐⭐ 更嚴重：接線檢查宣稱「掃描死題庫」，實際只回報寫死的布林值（2026-10-15 實測＋已修）

**這是本專案目前為止最接近「驗證工具本身無法被驗證」的一個實例**
（與 1zz 踩坑 #16「檢查工具本身必須有離開碼」同型）。

**症狀**：審計報告穩定回報 **3 個死題庫**（`order_bank`／`sort_bank`／`image_bank`），
`wiring` 維度 **40/100 🔴**，並建議「接線到 UI」。看起來像是三個沒上線的題庫。

**根因**：`dimWiring()` 的判定是
```ts
const dead = files.filter((f) => !f.wired && f.count > 0);
```
而 `f.wired` 來自 `BANKS` 陣列裡**手寫的布林值**（`wired: false`）。
檔案開頭的註解卻寫著「新增『接線狀態』檢查：找出有資料但**沒有任何程式引用**的死題庫」——
**宣告與實作不一致：它從頭到尾沒有讀過任何原始碼。**

**實測（三個都被 import）**：
```
order_bank.json → client/src/lib/classroomBank.ts:7   import orderSeed from ".../order_bank.json"
sort_bank.json  → client/src/lib/sortBank.ts:2        import sortBank from ".../sort_bank.json"
image_bank.json → client/src/lib/matchingBank.ts:6    import imageBank from ".../image_bank.json"
```

**解法（已修）**：新增 `scanWired()`，真的走訪 `client/src`／`server`／`shared`
尋找 `data/<檔名>` 字串。設計取捨：
- **排除 `scripts/`**——只被產生腳本引用的題庫，App 端看不到，對使用者仍是死的。
- **排除本檔自己**——`BANKS` 清單裡就寫著檔名，不排除會全部自我命中（自我實現的假陽性）。
- 比對字串用 `data/<檔名>` 而非裸檔名，避免寬鬆命中。

**修後**：`wiring` **40 → 100 🟢**，死題庫 3 → **0**（且 8 個題庫逐一人工複核過確實都有 client import）。

**⭐ 教訓**：
1. **一個「檢查」若只回報常數，它就是在說謊，而且會一直說同一套謊。**
   凡是宣稱「掃描／偵測」的欄位，要能指出它讀了哪個檔案、哪一行。
2. 這類錯誤**不會隨時間自己浮現**：寫死的 `false` 讓同一個誤報穩定重現，
   反而讓人以為「一直都有這個問題」，而更不敢質疑它。
3. 修的時候要**同時防兩個方向**：太寬（被 scripts 命中就算接線）與
   太窄（把自己也算進去）都會讓閘門失效。

### E2e. ⭐ 修 E2d 時順手踩到的：title 型題目用 `title` 去重會生出假重複（2026-10-15）

**症狀**：修好題幹檢查（改走 `stemOf`）後，「重複題目」從 84 組**變成 86 組**。

**根因**：去重鍵也跟著換成 `stemOf`，於是 title 型題目改用 `title` 當指紋。

### E2f. ⭐⭐ 又一個「宣告了但沒讀」：`gradeFromRange` 旗標從未生效，14 題配對組被誤報「grade=7 越界」（2026-10-16 實測＋已修）

**症狀**：審計報 `error 15`，其中 14 筆是 `mx-math-11` 等「grade=7 越界」。
`06-待辦` 據此把它們寫成**真缺陷 critical**：「`build-runtime-bank.mjs` 把 `grade>=7`
分流到已移除的國中檔 → 這 14 題永遠到不了使用者」。**這段推論是錯的，下面有證據。**

**根因（兩層）**：
1. **E2d 同型失效**：`BankFile.gradeFromRange?: boolean` 在 `BANKS` 裡逐檔宣告了
   （配對／排序／圖片五個檔都是 `true`），但**全腳本沒有任何函式讀它**。
   `loadBanks` 一律 `parseInt(gradeRaw)`，於是 `"7-9年級"` → 7 → 觸發 `> 6` 越界檢查。
2. **管線張冠李戴**：`mx-*` 配對組**根本不走 `build-runtime-bank.mjs`**。
   那條管線的來源只有 `taiwan_curriculum_500.json` 與 `generated_bank.json`
   （實測：`runtime_bank_elementary.json` 內 `mx-*` 出現 0 次）。
   `mx-*` 走 `client/src/lib/matchingBank.ts` 直接 `import` JSON。

**可達性證據（機械驗證，非推理）**：
- `MATCHING_SETS` 全部消費端（`paperExam.mixPaperMatching/mixPaperVariants`、
  `classroomBank.buildRelayRounds`、`MatchingPage`）**都不按 `set.grade` 過濾**
  ——只過濾「有無圖片」與「科目」。`MatchingPage.tsx:268` 甚至把 `set.grade`
  當文字標籤直接渲染（"7-9年級"）。
- 模擬執行期池：96 個純文字組中 14 個 `7-9年級` 組**全部在池內、可被抽到**。
- 但產品決策是「本站服務國小，內容等級上限六年級」（`adaptiveLearning.ts` 註解）。
  所以真正的問題不是「到不了使用者」，恰好相反：**14 組國中內容會混進國小試卷**
  （三年級學生可能抽到「國中代數公式」配對盤）。這是**另一種真缺陷**，
  與文件寫的缺陷方向相反。

**修法（已做，`error 15→1`）**：讓 `gradeFromRange` 真的被讀——
`Row` 增加 `_gradeFromRange`（檔案旗標 ∪ 逐列探測：非純數字字串即範圍標籤）；
`dimStructure` 對範圍列跳過 1–6 數值檢查；`dimCoverage`/`dimDiagnosis` 的年級矩陣
不歸入範圍列（"3-4年級" ≠ 單一年級，計入任何一格都是假的）。

**⭐ 教訓**：
1. **「宣告欄位 ≠ 生效欄位」是這個腳本的第二度同型病**（第一次是 `wired`，E2d）。
   判法：`grep -n "欄位名"` 若命中只有宣告處與 `BANKS` 字面值，就是死旗標。
2. **同一個症状（數字超出 1–6）至少有兩相反根因**：「資料壞了」vs
   「檢查器不懂資料格式」。這次文件選了**第三種**：「資料被管線丟了」——
   把 A 管線（build-runtime-bank）的規則套到 B 管線（matchingBank 直接 import）上，
   **兩條管線沒有交集卻被當成同一條**（E1 也是同管線誤會）。
   下次看到「X 進不了 App」，先找出 X 的**實際 import 鏈**再下結論。
3. 修正誤報時要**把被掩蓋的真問題重新表述**：14 組國中內容混入國小池這件事
   **已裁示並修掉（2026-10-16）**：走 B 方案——`MATCHING_SETS` 源頭以
   `gradeRangeCeiling(set.grade) <= MAX_GRADE` 過濾（99→85 組），資料檔保留不動，
   回歸鎖見 `matchingBank.test.ts`。選源頭而非逐消費端補，是因為消費端有 5 處
   （mixPaperMatching／mixPaperVariants／buildRelayRounds／pickMatchingSet／
   MatchingPage 索引循環），逐處補必漏其一——與 E2d「死旗標」同型：
   **規則要放在資料進出口的唯一真相處，不是散在每個讀取者**。

## E. 內容與閘門

### E1. ⭐ 生成器的「目標數字」對了，題目還是進不了 App（2026-10-02）

**症狀**：`qc:bank` 長期報「跨科題數量不足：應為 200，實際 120」，
但生成器的 `CROSS_SUBJECT_TARGET` **本來就是 200**，而且實測能產出 200。

**診斷關鍵：先問「200 題在哪裡」，不要直接想「怎麼補 80 題」。**

```
data/generated_bank.json          → 200 題跨科題（達標）
data/runtime_bank_elementary.json → 120 題（App 實際載入的）
```

**根因**：
- App 的年級範圍 `MIN_GRADE = 3` / `MAX_GRADE = 6`（`client/src/game/adaptiveLearning.ts`）
- 但配方 `grade` 寫到 **9**
- `build-runtime-bank.mjs` 分流到 `grade <= 6`（國小檔）／`grade >= 7`（國中檔）
- **國中檔早已被移除**，`grade >= 7` 那一路沒有檔案可寫
- 跨科題年級分布 `{3:7,4:30,5:40,6:43,7:52,8:19,9:9}` → **`grade 7–9` 剛好 80 題**

**⭐ 教訓**：
1. **補內容前先確認內容真的缺**。同一批資料在兩處數量不同，
   通常是**管線掉了**而不是產出不足。
2. **生成器的年級／範圍必須對齊 App 的實際常數**（`MIN_GRADE`／`MAX_GRADE`）。
   寫超出範圍等於白做——補了也會被同一個篩選丟掉。
3. **「移除某個輸出檔」會靜默改變分流結果**。移除國中檔時，
   `grade >= 7` 的題目沒有任何錯誤提示地消失了。
4. 順帶：只重生受影響的那部分（`subjectCombination` 有值的），
   不要跑 `bank:rebuild` 重生成全部 3766 題。

### E2. 跨科題缺口

同一題幹、不同選項組的題目是**展開變體**，是刻意的題庫設計，
不是瑕疵。把它當重複會導致錯誤的審計結論。

### E2. 答案位置分布

正解固定在同一格會讓學生靠位置猜。閘門要求任一位置佔比
在 25%±8% 內（樣本 ≥30）。

### E3. 資料不足時要標示「建置中」，不要顯示 0

顯示 0 會被誤讀成「沒有任何資料」，實際是「還沒建置」。
寧可說沒有，不要假裝有。

### E4. `qc:bank` 報「跨科題數量不足」是內容缺口不是 bug

目前 120／200。閘門 exit code 仍為 0（列為提醒不阻擋）。
