### 待站長決定：144 題沒有 `knowledge` 標籤

審計把它標為 critical「診斷系統無法運作」，但**證據指向這是規格問題，不是資料損壞**：

```
缺 knowledge 的 144 題 ＝ 6 個 title 型題庫的全部
  fill_bank 24 ／ order_bank 16 ／ sort_bank 5
  image_bank 3 ／ matching_bank 30 ／ matching_bank_extra 66
以上題庫的 schema 是 id/subject/grade/difficulty/title/instruction/pairs|categories
—— 結構上就沒有 knowledge 欄位。
```

而 `runtime_bank_elementary`（3175 題，App 主要題庫）**全數都有 knowledge**。
`matchingBank.ts` 的註解也明說它「不進後端 question_bank、不進戰鬥抽題」。

**兩種讀法，需你裁定**：
1. **活動型題庫本來就不該進診斷** → 審計的 critical 是過度告警，
   應在 `dimKnowledge` 排除這些題型（比照 1／2 年級無題的處理）。
2. **希望活動題也能被診斷** → 那要為 144 題補 knowledge 標籤，
   這是內容工程，工作量明確但需要教學判斷。

**我不代為決定**，因為這取決於產品要如何看待「配對／分類歸位」這類活動
在學習診斷裡的角色。

## 給下一位 agent 的提醒

### 動手前必讀

1. **[05-踩坑與陷阱](05-踩坑與陷阱.md)** —— 尤其 A 區（部署）與 C 區（程式寫作）
2. **[03-本機工作台](03-本機工作台.md)** —— 這台機器的 node、指令、驗證序列
3. **本專案的既有慣例**（不要憑通用知識）：
   - 每個 `.tsx` 都要 `import React`（`jsx: preserve` → 經典 JSX 轉換）
   - `Map` 迭代要 `Array.from(...)`
   - JSX 純文本不能用 markdown 語法

### 驗證不能省

- 改完跑齊：**tsc → vitest → 六道閘門 → build**
- 碰登入／權限的改動：**做本機端對端**（啟動指令見 [03](03-本機工作台.md)），
  不要只靠單元測試
- 上線後要**線上實測**，不要只看部署成功

### 幾個容易走錯的方向

- **不要在測試失敗時改測試**——先問「是測試錯還是設計錯」。
  本站至少有一次是設計問題（命名撞車），修的是設計。
- **不要加假數字**。本站後台每個數字都標明來源與快取時間。
  拿不到資料就顯示「無法取得」＋原因，不要填 0 或估算值充當精確值。
- **不要在後台顯示機密值**。只顯示「是否已設定」。

### 更新這份知識庫

- 新增踩坑 → 追加到 [05](05-踩坑與陷阱.md)，用「症狀 → 根因 → 解法」格式
- 完成一輪工作 → 在 [04](04-工作執行紀錄.md) 加一節並附 commit hash
- 有新決策 → 在 [02](02-架構與關鍵決策.md) 記下**為什麼**
- **新增文件只要放一個 `.md` 進 `docs/knowledge-base/`**，後台會自動收進清單，
  不需要改任何程式碼

## 站長日常動線（後台的閱讀順序）

後台分組刻意對應巡檢順序：

1. **營運與資源** —— 站點現在忙不忙、有沒有在噴錯
2. **內容與題庫** —— 裡面裝了什麼
3. **成本與用量** —— 這些東西花多少錢
4. **存取與角色** —— 誰能進來、以什麼身分
5. **維護工具** —— 我要動手做什麼
6. **系統與部署** —— 它跑在什麼上面
7. **知識與文件** —— 想知道為什麼這樣做時，看這裡
