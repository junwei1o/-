## 依時間倒序

### 2026-10-02 晚間 · 站長安全性收緊 ＋ 壓縮中介層審查

**① 站長用戶名從前端 bundle 移除**
原本前端寫死 `ADMIN_USERNAME = "admin"` 來比對——但 **bundle 是公開的**，
任何人看 JS 就讀得到（與 2026-09 那次 PAT 寫死在 git remote 同一類問題）。
改成前端**只認得「是不是自己的船名」**，其他一律問後端。
好處：改 `ADMIN_USERNAME` **只改部署環境**即可，不必動程式、不必重新部署前端；
且猜中與猜錯**打到後端的請求完全相同**，無法用介面列舉。

**② 壓縮中介層深度審查**（`httpCompression`，並行 agent 寫的）
- ⭐ 抓到一個**實測可重現**的正確性問題：`Vary` 被後設的 `setHeader` 覆蓋，
  導致中間快取可能把 brotli 內容發給不支援的客戶端。已修（見 05 的 D7）。
- 加了一道**緩衝上限護欄**（8 MB）：這個中介層是緩衝式的，原先沒上限，
  日後有人加一個會回傳大 JSON 的 GET 端點就會線性吃記憶體，免費層只有 512 MB。
  超過上限就放棄壓縮、原樣送出——傳輸多一點，換記憶體有上限。
- 順帶確認：單層壓縮（無雙重壓縮）、`Content-Length` 與實際 bytes 一致、
  串流 71 MB 下載後伺服器存活。

### 2026-10-02 · 站長後台第四輪深化 —— 8 分組 19 模組

站長回報「已經設定完成」後要求繼續深化。前一輪掃描確認線上 13 模組 / 7 分組**一個都沒少**，
本輪針對「站長要捲過所有模組才能拼出結論」與「完全沒有一類資料」兩個問題深化。

- **新分組「站長總覽」（order 5，排在巡檢動線之前）**——因為「先看這裡」是整頁的前提
- **健康總表**：6 個子系統紅黃綠燈，**判斷門檻寫在畫面上**（看到紅燈要能立刻知道是什麼條件觸發的）
- **學習活動實況**：後台原本**完全沒有**「有沒有人在用」這類資料——對 learning 站台是站長最先該知道的
- **功能降級狀態**：「功能 → 需要什麼 → 現在有沒有」的對照，直接回答「為什麼某功能沒生效」
- **資料安全與備份**：⭐ 掃描時發現 `/api/backup` **無需認證即可下載 8.4 MB 全站原始碼**——
  這是**刻意公開**的功能（站長要能離線架站），但「公開」該是知情的選擇，已在後台明白寫出
- **維運操作審計**：記憶體環形緩衝，記錄誰在什麼時候執行了維運操作
- **部署與版本**：可判定的版本訊號（不給容易誤導的 bundle 雜湊）

**驗證**：tsc 0｜185 檔 / 1416 測試全綠（+11）｜六閘門全 PASS｜build ✓｜**Playwright 自檢 29/29 通過**

#### 本輪修掉的兩個真實缺陷
1. **審計紀錄靠 30 秒輪詢才更新** → 站長按完「執行健康檢查」轉頭看審計紀錄是空的，以為功能壞了。
   已讓維運操作成功後立即 invalidate `auditLog`。
2. **審計排序在同毫秒內失效**（`Date.now()` 只有毫秒解析度）→ 連續兩次操作順序會錯。
   已加單調遞增序號作 tiebreaker。
