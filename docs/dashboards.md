# 診斷儀表板規格（老師端／學生端）

> 建立：2026-09-30｜依賴：`docs/diagnosis-system.md`、`docs/question-types.md`
> 狀態：**目標設計已定案，但老師端被資料通道硬阻塞**（見 §2）

---

## 0. 一句話

**老師端要的是「我該教什麼」，學生端要的是「我該做什麼」。**
兩者共用同一套 `StudentDiagnosis`，只是呈現方式與語氣不同。

---

## 1. 目標設計（已定案）

### 1.1 老師端：三層鑽取

```
第一層 班級總覽 ──點知識點──▶ 第二層 知識點詳情 ──點學生──▶ 第三層 學生個人檔案
```

| 層 | 第一眼看到 | 核心元件 |
|---|---|---|
| 第一層 | 全班緊急事項（3 張卡） | 知識點熱力圖、學生×知識點矩陣、本週 vs 上週 |
| 第二層 | 該知識點的全班狀況 | 信心分佈、各難度／各題型表現、最常錯題 TOP 5、需補救名單、教學建議 |
| 第三層 | 該學生 | 知識點雷達圖、強項／需加強、錯題本、近期表現、建議行動 |

### 1.2 學生端：正向優先 + 遊戲化

| 原則 | 說明 |
|---|---|
| 正向優先 | 先顯示強項，再顯示需加強 |
| 具體可行 | 不說「你要多練習」，而是「做這 5 題」 |
| 不製造焦慮 | 「這塊还可以再加油」，不用「你很差」 |
| 隱私 | **不顯示其他同學、不顯示班級排名** |
| 年齡適配 | 國小學生看得懂的用字 |

主畫面：今日任務（系統推薦）→ 我的強項 → 需要加油 → 我的進步 → 徽章牆。
遊戲化：等級 7 階（見習船長→船長之星）、8 種徽章、連續天數。

### 1.3 共用

| 狀態 | 顏色 | 門檻 |
|---|---|---|
| 已掌握 | 🟢 | confidence ≥ 0.75 |
| 穩定 | 🟢 | 0.55–0.75 |
| 不穩定 | 🟡 | 0.35–0.55 |
| 盲點 | 🔴 | < 0.35 |
| 樣本不足 | ⚪ | attempts < 3 |

## 2. 🔴 前置條件（老師端被硬阻塞）

### 2.1 實測：雲端同步只帶 3 個數字

`client/src/game/cloudSync.ts` 的實際型別：

```ts
export interface CloudPayload {
  v: 1;
  rpg: string | null;   // RPG 狀態（整包字串，非結構化）
  bx: string | null;    // BX 狀態
  savedAt: number;
}
export interface CloudMetrics {
  coins: number;
  totalAnswers: number;   // ← 只有總數
  badges: number;
}
```

**沒有** per-question 明細、**沒有** `knowledge`、**沒有** `difficulty`、**沒有** `questionType`。

### 2.2 逐題明細從不上傳

`LearningRecord = { questionId, subject, isCorrect, errorType?, timestamp, flagged }`
只存在學生本機 `localStorage`，雲端同步**不含**它。

### 2.3 沒有班級維度

身分機制是「船長名字」（`cloud.register/load/save` 皆以 `name` 為鍵），**沒有 `classId`**。
老師端要的「三年甲班 45 人 × 自然科」在資料模型裡不存在。

### 2.4 即使通道打通，知識點級診斷仍不可信

`audit-report.json`（3063 題實測）：

| 指標 | 實測值 | 影響 |
|---|---|---|
| 唯一知識點標籤 | 2228 | — |
| **只出現 1 次的標籤** | **1629（73%）** | 知識點級統計無法收斂 |
| 平均每題標籤數 | 1.65 | 歸因粒度不足 |
| 知識點樣本 < 3 | **1835 個** | 信心分數落在「樣本不足」 |
| 重複題 | **81 組** | 同一題答兩次＝兩個假樣本 |

### 2.5 結論

| 端 | 現在能做 | 被阻塞的部分 | 阻塞原因 |
|---|---|---|---|
| **老師端（班級）** | ❌ 幾乎全部 | 三層鑽取全部 | 缺逐題明細上傳、缺 classId、缺知識點品質 |
| **學生端** | 🟡 部分（見 §3） | 知識點級信心、今日任務推薦、徽章中的知識點類 | 缺作答訊號（用時／重做／改答）＋知識點品質 |

## 3. 現在就能做的（學生端第一版）

資料來源：本機 `LearningRecord` + `DailySignIn` + RPG 狀態（皆已存在）。

| 區塊 | 可用資料 | 限制 |
|---|---|---|
| 連續天數 / 等級 / 金幣 | `getDailySignIn()`、RPG 狀態 | ✅ 完整可用 |
| 整體正確率與趨勢 | `getLearningRecord()` 按週聚合 | ✅ 完整可用 |
| 錯題本 | `getMemoryAlarmCount()` | ✅ 完整可用 |
| 各科正確率 | `LearningRecord.subject` | ✅ 可用（僅科目層） |
| **知識點級信心** | 需 `knowledge` + 作答訊號 | ⚠️ **退化為修正後正確率**，且標籤 73% 單例 |
| 今日任務推薦 | 需知識點級診斷 | ⚠️ 只能退化為「依科目推薦」 |
| 徽章（知識點類） | 需知識點級信心 | ⚠️ 僅「連續 N 天／完成 N 題」類可先做 |

> **建議的第一版**：連續天數、等級、整體正確率趨勢、各科正確率、錯題本、非知識點類徽章。
> **明確標示**「知識點分析建置中」——不要用退化資料假裝知識點診斷。

## 4. 解鎖老師端的最小路徑（依序）

| 順序 | 任務 | 為何必須先做 |
|:---:|---|---|
| 1 | **標準化 `knowledge` 標籤**（建 `docs/knowledge-taxonomy.md`） | 沒有它，任何知識點級呈現都是雜訊（73% 單例） |
| 2 | **去重 81 組重複題** | 重複題會製造假樣本，直接污染診斷 |
| 3 | **作答訊號埋點**（`timeSpentMs`／`retryCount`／`changedAnswer`） | 信心分數的輸入；缺它則退化為正確率 |
| 4 | **逐題明細上傳**（擴充 `CloudPayload` 或新增 `cloud.records` 端點） | 老師端的唯一資料來源 |
| 5 | **班級維度**（`classId`／學生名冊／老師-班級關聯） | 老師端的前提 |
| 6 | 老師端第一層 → 學生端主畫面 → 老師端第二、三層 | UI 最後做 |

**注意順序**：1→5 全是資料與內容工作，UI（第 6 步）排最後。
**先做 UI 會得到一個漂亮的空殼**——這正是目前 `StudentDiagnosis` 的處境（引擎完成、無呼叫點）。

## 5. 隱私（沿用既有框架，不得放寬）

| 規則 | 說明 |
|---|---|
| 學生看不到其他同學 | 任何形式的同儕比較都不顯示 |
| 不顯示班級排名 | 避免焦慮 |
| 不顯示絕對分數 | 用進度條與百分比 |
| 家長僅能看自己孩子 | 需登入驗證 |
| AI 導讀不含個資 | 不得含姓名／學校／班級（既有隱私框架） |

> ⚠️ **第 4 步（逐題明細上傳）是隱私敏感變更**：一旦上傳，學生的逐題作答就離開本機。
> 需先更新隱私說明並取得同意——**既有文案寫的是「預設只在你的瀏覽器裡記錄」**，
> 這個承諾會因此改變。實作前必須先處理這件事。
